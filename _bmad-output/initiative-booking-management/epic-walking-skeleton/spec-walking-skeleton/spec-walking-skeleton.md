# Epic 0: Walking skeleton

## Why

This is a vision to realize and a risk to retire. SlotBook is built by a sandbox agent
through a PR review loop (ADR-0004), and that loop has only run on a throwaway story.
Before product features exist, the thinnest possible end-to-end slice must prove that
the pipeline delivers working code across both sides: API, UI, tests and CI, merged
through review. That slice then gives the PRD and architecture work a real codebase to
land on (Option C, 2026-10-09).

## Capabilities

- **CAP-1**
  - **intent:** An operator or probe can ask the API whether it is alive.
  - **success:** `GET /health` returns 200 with JSON `{"status":"Healthy"}`. An integration test (`WebApplicationFactory`) asserts the status code and the body.
- **CAP-2**
  - **intent:** A visitor opening the web app sees whether the API is reachable.
  - **success:** The page shows a healthy state when `/health` answers 200, and an unavailable state on a network error or a non-200 response. Component tests cover both states, with HTTP mocked.
- **CAP-3**
  - **intent:** The developer can run both sides locally and see the frontend reach the API.
  - **success:** From a clean clone, following the README (start the API, then start the frontend) opens a browser page showing the healthy state.
- **CAP-4**
  - **intent:** Every PR is built and tested automatically for the side or sides it changes.
  - **success:** A PR touching only `src/frontend` runs only the frontend build and tests, and the reverse holds for `src/backend` and `tests/backend`. A failing test turns the required check red, and the PR can't be merged.

## Constraints

- **Stack and layout:** follow ADR-0003, ADR-0005 and ADR-0006.
  - .NET 10 and Angular 22.
  - `src/backend`, `src/frontend` and `tests/backend`, with a root `SlotBook.slnx`.
  - xUnit v3 + Shouldly for the backend, and Vitest/jsdom with npm for the frontend.
  - Test commands: `dotnet test` from the root, and `npm test` in `src/frontend`.
- No database, persistence, auth or tenancy.
- The backend is a single API project. No Clean Architecture layers or modules until the architecture document and ADR-0002 decide them.
- The frontend and backend share only the HTTP contract. Neither references the other's folder.
- Each story is one PR, built in one sandbox run. Every test runs in the sandbox, with no browser and no external services.
- Generic naming only: the product is SlotBook, with no client branding.
- **CI shape:** one workflow detects which side changed and runs only that side's jobs. An aggregate job always runs, fails if any job that ran failed, and is the only required check on `main`. A skipped workflow never reports, so per-side required checks would block every merge.

## Non-goals

- Deployment or cloud resources of any kind (Azure is a later epic)
- A database, or migrations
- Auth or tenancy
- Logging or telemetry beyond the framework defaults
- Browser end-to-end tests (Playwright)
- UI design, a component library, i18n or RTL
- Container images for the app
- CORS configuration for production

## Success signal

- **Locally:** on a clean clone, the web page reports the API healthy.
- **Through the pipeline:** every Epic 0 PR was produced by the sandbox and merged through the review loop.
- **In CI:** both the backend and the frontend checks are green on `main`.

## Assumptions

- `/health` sits at the API root (not under `/api`) and is a liveness check only, because nothing exists for it to depend on yet.
- The local run reaches the API through the Angular dev-server proxy, so the API has no CORS configuration in Epic 0.
- Files generated by the Angular CLI and the `dotnet new` templates don't count toward the story size limit of about 10 files.
