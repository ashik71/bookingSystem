# The web page shows the API's health

## Description

This is the first code in the repo. It creates the .NET 10 solution with one API project
and its test project, and the Angular 22 app, laid out as ADR-0006 says. The API answers
`GET /health`, and the app's only page shows whether the API is healthy or unavailable.
Both sides have tests, and the README explains how to run them locally. It is the tracer
bullet for the epic, and story 2's CI builds on its test commands.

## Acceptance Criteria

1. **The API reports itself healthy**
   **Given** the API is running
   **When** a client sends `GET /health` with no credentials
   **Then** the response is 200 with content type `application/json` and the body `{"status":"Healthy"}`
2. **The page shows a healthy API**
   **Given** `GET /health` answers 200
   **When** a visitor opens the app's root page
   **Then** the page shows that the API is healthy
3. **The page shows an unavailable API**
   **Given** `GET /health` fails with a network error, or answers with any status other than 200
   **When** a visitor opens the app's root page
   **Then** the page shows that the API is unavailable
   **And** the page still renders, with no unhandled error
4. **The tests prove criteria 1–3**
   **Given** a clean clone in the sandbox
   **When** `dotnet test` runs from the repo root and `npm test` runs in `src/frontend`
   **Then** both pass, and `npm test` exits once it finishes (no watch mode)
   **And** an integration test (`WebApplicationFactory`, xUnit v3, Shouldly) covers criterion 1, and component tests with HTTP mocked cover criteria 2 and 3
5. **A developer can run both sides from the README**
   **Given** a clean clone on a machine with the .NET 10 SDK and Node 24
   **When** the developer follows the README: start the API, then start the frontend
   **Then** the browser page shows the API healthy
   **And** the frontend reaches the API through the Angular dev-server proxy, and the API has no CORS configuration
6. **The layout and build settings follow ADR-0006**
   **Given** the finished change
   **When** the solution builds
   **Then** every project targets `net10.0`, package versions are set centrally, and the build has no warnings, because warnings are errors
   **And** Angular is pinned to major version 22 in `package.json`, and neither side references the other's folder

## Boundaries

- Must not change: the board-sync workflow, the planning docs, the ADRs, or `CLAUDE.md`.
- Must not add: a database, persistence, auth, tenancy, logging or telemetry beyond the framework defaults, CORS, or Clean Architecture layers. The backend is one API project.

## Notes

- Decision: `/health` sits at the API root, not under `/api`, and is a liveness check only (2026-10-09).
- Decision: files generated by the Angular CLI and the `dotnet new` templates don't count toward the story size limit of about 10 files (2026-10-09).
- No design exists, and UI design is a non-goal. The page is plain text showing the status; the builder chooses the wording and layout.
- Risk is low because nothing is deployed and there are no users. A wrong result costs only rework.
