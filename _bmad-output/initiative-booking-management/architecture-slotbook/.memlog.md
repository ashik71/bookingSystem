- (decision) D2 Tenancy: one database, shared collections, tenantId on every tenant-owned document. Rules: (1) tenant is in the API route /api/t/{tenant}/...; every session (patient or staff) carries a tenant claim; a route-scope authorization check (P-11) compares them before any handler runs, mismatch = 403; (2) the repository/unit of work applies the tenant filter on every read/write and stamps tenantId on insert - handlers never write tenant filters by hand; (3) every unique index begins with tenantId; (4) a fitness test requires every aggregate to be tenant-owned or explicitly marked global; the cross-tenant suite (SC-2) proves the rest. The frontend maps the clinic's address to its tenant; the API only trusts the route + claim. Binds: all epics. Prevents: per-handler tenant filters that one story forgets; Host-header tenant resolution that breaks behind the static-site proxy. Rejected: database per tenant (Atlas free 500-collection cap ~30 tenants; per-tenant index setup), collection per tenant. Wrong when a tenant needs contractual isolation (own DB/region/key) or noisy-neighbour separation; migration = copy by tenantId. Developer accepted.
- (decision) D3 Concurrency: ONE INVARIANT, ONE GUARD DOCUMENT - every write path that touches an invariant writes that invariant's guard document in the same transaction, turning write skew (possible under MongoDB snapshot isolation) into write-write conflicts that abort and retry. Guards: Slot (capacity counters free/reserved/taken, nextSeq, status) written by book, cancel, reserve, release, lower capacity, close, publish; Patient ledger (per tenant+number: active count, per-week counts) written by patient book and cancel; Booking (state) written by check-in, cancel, lapse. Ticket-code uniqueness: partial unique index (tenantId, code) where codeLive=true, a daily job clears codeLive for past slot dates (lag only wastes codes). Same number twice in one slot: partial unique index (tenantId, slotId, patientId) where the booking holds a place. Aggregates: Slot, Booking, PatientLedger separate (Slot NOT inside Booking); Week owns publication and publishing writes its slots. Write mechanism (option A): handler loads aggregates, aggregate methods enforce rules, unit of work saves each with version in the filter, all in one multi-document transaction, write concern majority, read concern snapshot; a write conflict / version conflict / transient transaction error re-runs the whole handler up to 5 times with jitter; side effects only via the outbox. Rejected: bookings embedded in Slot (limit and code still cross-document; document growth; awkward my-bookings queries), conditional $inc rules-in-filters (rules leave the domain). Wrong when the Atlas free 100 ops/s cap (~7 ops per booking => ~14 bookings/s) misses NFR-13 at the publication peak: first optimise only the booking path to a single conditional update, then a paid tier; the guard-document rule stays. Developer accepted.
- (constraint) MongoDB transactions (manual, production considerations, checked 2026-10-10): reads use a snapshot (can be stale); a write to a document modified after the snapshot aborts with a write conflict; lock wait 5 ms then abort; transaction lifetime < 60 s by default; on error, abort and retry the whole transaction.
